A GitHub-hosted runner vs a self-hosted runner

Both run the same workflow YAML. The difference is whose machine the steps run on: a hosted runner is a fresh VM GitHub throws away after each job. A self-hosted runner is your box, so it can reach your private network, and it keeps whatever the last job left behind.

1. GitHub-hosted runner

runs-on: ubuntu-latest. You write YAML, GitHub brings the machine.

Every job starts on a clean machine, so nothing leaks between jobs. The price: it can only reach what is on the public internet.

2. Self-hosted runner

Same workflow syntax, your machine. GitHub still schedules the job.

GitHub still decides when a job runs, but the steps execute on a box you own. The runner dials out, so no inbound port opens, and the job can reach the private network the hosted VM never sees.

S-T: a hosted runner is a rental car, cleaned between drivers. A self-hosted runner is your own car: it gets into the private garage, but whatever the last driver left on the seat is still there.

One job, both worlds

"Run the tests on every push to main"

GitHub-hosted

  1. A push fires the on: push trigger.
  2. GitHub boots a clean ubuntu-latest VM.
  3. The steps check out the code and run npm test.
  4. Logs upload, the check goes green or red, the VM is destroyed.

Self-hosted

  1. A push fires the trigger in the workflow file. repo
  2. GitHub queues the job and matches [self-hosted, linux] to an idle runner. GitHub
  3. The runner's long poll picks the job up with a short-lived token. GitHub
  4. The steps run in _work/ on your box and can hit the staging DB. your box
  5. Logs stream back and GitHub sets the check status. GitHub
  6. The workspace stays on disk for the next job. gap
