From a Compose service to Kubernetes objects

A docker-compose.yml service puts everything about one container in one block: image, ports, environment. Kubernetes splits the same facts across separate objects, because running a container and reaching it are different jobs there. Colors track the same value across both shapes.

You write it (in the repo) The converter does it Cluster objects

1. Same service, two shapes

Image in blue, ports in amber, environment in green. The dashed amber curve: one compose port string becomes two Kubernetes fields.

The 8080:80 string carries two ports. The container port (80) lands on the Deployment; the published port (8080) lands on the Service.

S-T: compose is one index card per app. Kubernetes files the same card into separate drawers: "what to run" (Deployment) and "how to reach it" (Service).

Why split it at all?

Four reasons the extra objects earn their keep.

1

Many hosts

Compose targets one machine. A Deployment can place replicas on any node, so the address can't live on the container.

2

Stable address

Pods come and go. The Service keeps one name and port while the pods behind it change.

3

Separate lifecycles

Rolling out a new image touches the Deployment only. The Service, and every client using it, stays put.

4

Not 1:1

depends_on and build: have no direct twin. Startup order becomes readiness probes; builds need an image in a registry.

2. How one service becomes several objects

One compose block in, one object per concern out.

The converter is a starting point. Review its YAML before applying it: resource limits, probes and secrets usually need hand edits.

One service, end to end

"Move the web service from compose to a cluster"

  1. You already have services.web in docker-compose.yml. repo
  2. kompose convert writes web-deployment.yaml and web-service.yaml. tool
  3. You add probes and resource limits, and move secrets out of env:. repo
  4. kubectl apply -f . creates the objects. cluster
  5. The scheduler places the pod on a node; the Service routes 8080 to pod port 80. cluster

Unverified: this page is a layout example for the sketch skill, not checked against a live cluster. Converter output (file names, defaults) varies by version. nginx:1.27 and LOG_LEVEL are illustrative.
